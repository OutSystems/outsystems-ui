# Review Staged Changes

Review the changes currently staged for commit (`git diff --cached`) against this repo's conventions. Focus on correctness, style, and architectural fit — not PR-level concerns like description, labels, or CI.

---

## Conventions to enforce

@.claude/rules/scss.md
@.claude/rules/typescript.md

---

## How to run the review

1. **Survey what's staged**
   - `git diff --cached --stat` to see the file set and scope.
   - `git diff --cached --name-only` to get the path list.
   - Classify by extension/location:
     - `*.ts` → TypeScript rules apply
     - `*.scss` → SCSS rules apply
     - Generated entry files (`O11.OutSystemsUI.scss`, `ODC.OutSystemsUI.scss`, `O11.OSUIFramework.ts`, `ODC.OSUIFramework.ts`) → flag as likely hand-edit, should be regenerated instead
     - `gulp/ProjectSpecs/**` → structural build changes, call out explicitly
     - `specs/**`, `*.md` → documentation; sanity-check only
   - If a file type falls outside TypeScript / SCSS / docs, note it and keep going — don't block.

2. **Read the actual diff**
   - `git diff --cached` for the full patch. Do not skim; every hunk gets looked at.
   - For large diffs, process file-by-file using `git diff --cached -- <path>`.

3. **Apply the rules file that matches each hunk**
   - TypeScript hunks → TypeScript rules (naming, namespaces, provider isolation, JSDoc, CreateApiResponse wrapper, ErrorCodes, registry pattern, AMD/no-imports, no `enum`).
   - SCSS hunks → SCSS rules (`$token-*` preference, `--osui-{component}-{prop}` API, no `--font-size-*`/`--shadow-*` reintroduction (`--color-*`/`--space-*` are the theme layer, not retired), no helper-function use, dark-theme invariant, no hand-edit of generated entry files, data-attribute widgets).

4. **Cross-file checks** (things the per-hunk view misses)
   - New pattern? Verify it has all four pieces: `<Name>.ts` + `<Name>Config.ts` + `I<Name>.ts` + `<Name>API.ts` (+ `<Name>Factory.ts` if provider-backed).
   - New ErrorCode referenced in a public API? Confirm it's declared in `src/scripts/OSFramework/OSUI/ErrorCodes.ts`.
   - New pattern name used? Confirm `GlobalEnum.PatternName.*` entry exists.
   - New SCSS partial? Confirm it's registered in `gulp/ProjectSpecs/ScssStructure/*.js` — otherwise the build won't pick it up.
   - New provider override SCSS? Confirm the consuming pattern `@import`s it.
   - Third-party library version bump? Cross-reference ARCHITECTURE.md external integrations table.

5. **Smell-test the diff for hand-edits of generated output**
   - `dist/**` — never staged. Flag if present.
   - `src/scss/O11.OutSystemsUI.scss`, `src/scss/ODC.OutSystemsUI.scss` — regenerated by gulp. Flag any diff here as "wrong layer — edit the matching `gulp/ProjectSpecs/ScssStructure/*.js` spec and re-run `npm run dev`".
   - `src/scripts/OutSystems/O11.OSUIFramework.ts` / `ODC.OSUIFramework.ts` — same category.

6. **Report format** — one section per severity:

   ```
   ## Blockers  (must fix before commit)
   - <file>:<line> — <one-line explanation> — <rule reference, e.g. "typescript.md §3 — private member missing `_`">

   ## Warnings  (should fix; acceptable with justification)
   - <file>:<line> — <explanation> — <rule reference>

   ## Nits  (stylistic, optional)
   - <file>:<line> — <explanation>

   ## Notes
   - Architectural observations, cross-file follow-ups worth spawning as separate tasks, etc.
   ```

   If the diff is clean, say so plainly: "No issues against the rule set. Staged change is OK to commit." Don't invent problems.

## Ground rules for the review

- **Don't edit anything.** This command reads + reports. If a fix is obvious, describe it in the Blocker/Warning line; leave the change to a follow-up.
- **Cite the rule file and section** for every Blocker/Warning. `scss.md §3` or `typescript.md §5`. Lets the author verify the reasoning.
- **No nit-spam.** If the file has 20 formatting inconsistencies that pre-date this diff, don't list them. Focus on what the staged hunk introduces or changes.
- **Respect scope.** If the author is mid-migration (e.g. a single SCSS file being token-backed), don't demand they also fix unrelated legacy in the same file.
- **Be direct.** Terse findings beat hedged prose. No "consider maybe perhaps" — either it violates the rule or it doesn't.
