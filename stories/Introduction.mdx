# OutSystems UI — Storybook

This Storybook documents the **OutSystems UI** pattern library by driving the
**compiled bundle** exactly the way OutSystems Service Studio does at runtime —
transcribed to high-code.

## How it works

OUI patterns are not React/Vue components: they are TypeScript behaviour classes
that attach to HTML that the OutSystems platform renders. At runtime the platform:

1. renders an HTML skeleton (specific classes / `name` attributes per pattern),
2. calls `OutSystems.OSUI.Patterns.<Pattern>API.Create(id, configsJSON)`,
3. calls `…Initialize(id)`, which runs the pattern's `build()`.

Each story here reproduces those three steps:

- `.storybook/preview-head.html` loads the compiled bundle
  (`dist/ODC.OutSystemsUI.{js,css}`) and the provider vendor libs
  (Flatpickr, Splide, noUiSlider, VirtualSelect) as classic `<script>` tags,
  exposing `OutSystems.OSUI.*` and `window.flatpickr` etc. as globals.
- `stories/_helpers/osui.ts` provides `renderPattern(template, init)` — it
  injects the HTML, runs `init` after mount, and disposes the previous story's
  instances so the registry doesn't leak.
- The HTML skeletons are **derived from each pattern's TypeScript contract**
  (`Enum.ts` classes, `Config` defaults, the selectors `build()` queries) — not
  from an OML.

## Prerequisite

The compiled bundle must exist before starting Storybook:

```bash
npm run build:osui      # one-shot gulp production build (ODC)
npm run storybook
```

## Patterns covered

Stories exist for every public pattern API, grouped by category:

- **Content** — Accordion, Carousel, FlipContent
- **Interaction** — AnimatedLabel, BottomSheet, ButtonLoading, DatePicker, Dropdown, MonthPicker, Notification, RangeSlider, Search, TimePicker, Tooltip
- **Navigation** — OverflowMenu, SectionIndex, Sidebar, Submenu, Tabs, Wizard (+ WizardItem)
- **Adaptive** — Gallery
- **Numbers** — Progress (Bar + Circle), Rating
- **Utilities** — InlineSvg, Video, SwipeEvents, TouchEvents

Provider-backed patterns load their vendor global first (Flatpickr +
monthSelect plugin for the pickers, Splide for Carousel, noUiSlider + wNumb for
RangeSlider, VirtualSelect for Dropdown).

**Not yet storied:** `DropdownServerSideItem` — it's the server-side Dropdown
variant and needs the server-side parent + a data source to render meaningfully.

## HTML / CSS-only blocks

Many OutSystems UI components have **no JavaScript** — they're pure markup styled
by the shipped stylesheet (rendered as static blocks in low-code). These are
storied too, via `renderStatic(template)` (no `Create()`/`Initialize()`), using
the **shipped** class names taken from each `_*.scss`:

- **Content** — Alert, Card (Basic/Sectioned/Background/Detail), Tag, UserAvatar, ChatMessage, Section, BlankSlate, ListItem, Table
- **Navigation** — Breadcrumbs, Timeline, Pagination
- **Adaptive** — MasterDetail (`.split-screen-wrapper`), Columns
- **Numbers** — Badge, IconBadge, Counter
- **Interaction** — Popup

Note these use shipped classes, which sometimes differ from the proposed
showcase names (e.g. Master Detail ships as `.split-screen-wrapper`, Chat as
`.chat`, Breadcrumbs items as `.breadcrumbs-item`).

Every story (JS + static) is smoke-tested headless (loads, initialises / renders,
no console errors). Use any existing story as the template when adding new ones.

## Platform Widgets (a different stack)

Some OutSystems UI controls are **not** part of this CSS/TS library — they are
**React** components shipped from `@outsystems/runtime-widgets-js`, the platform
runtime, published only to the OutSystems-internal package feed.

This repository is public, so it does **not** depend on those packages. Instead
the **`Widgets/`** group renders each widget's real DOM as static markup:
Button, ButtonGroup, Checkbox, RadioGroup, Switch, Input, TextArea, Dropdown,
Upload, Link, Popup, Popover, Label, Icon, Image, Text, plus the CSS-only
FeedbackMessage, List and Table blocks.

The markup is not guesswork. Each story is a transcription of the DOM captured
from `@outsystems/runtime-widgets-js@6.25.4` mounted under React 17 — every tag,
class, `data-` attribute and ARIA attribute the widget actually emits, with the
provenance recorded in the story's own doc comment. Where a story deliberately
departs from the capture (real `id`s instead of the harness's empty ones, a
`selected` attribute the DOM `value` property could not express) the comment says
so and why.

The visible form of the data-attribute controls comes from the **platform base
CSS** (`/platform/platform-core.css`), a tracked Storybook-only copy of the
platform's base layer. It loads *before* the OUI stylesheet, exactly as it does
in a real app: it generates the checkbox box and the switch track/thumb with
pseudo-element `content`, and OUI then recolours and resizes them. That override
is precisely what these stories exist to catch.

**They are still usable.** Most of these widgets are native controls underneath, so
transcribing them changed nothing: the checkbox and switch toggle, the radios are
mutually exclusive, the inputs are editable, Upload opens a file dialog, the native
Dropdown is a real `<select>`. The three that changed state through their own
JavaScript — ButtonGroup selection, the custom Dropdown's expand/pick/collapse, and
Popover's expand/outside-collapse — are re-wired with a handful of listeners that apply
exactly the class and DOM mutations the real widget applies, verified by comparing the
result against the live widget's DOM captured after a real click. `Dropdown → Custom
Expanded` and `Popover → Expanded` additionally pin those states open, because Chromatic
photographs the initial render only.

Note that the **`iconLibrary` toolbar toggle does not change `Widgets/Icon`**, and never
could: the platform Icon widget hardcodes FontAwesome classes (`fa fa-star`), and OUI's
bundle carries no `.fa-*` rule for the toggle to reach — it only swaps the `--osui-icon-*`
properties OUI's own pseudo-element icons read. The story therefore shows both libraries
side by side instead of pretending the toggle applies.

**Consequence worth knowing:** the whole Storybook builds from a plain
`git clone && npm i && npm run build && npm run build-storybook`, with no
internal access, on any branch, from any fork. What you see locally is what CI
snapshots.

> Trade-off: static markup cannot drift-detect the platform. If the platform changes a
> widget's DOM — or how a control behaves — these stories keep passing against the old
> shape. The refresh trigger and re-capture method are documented in
> `docs-internal/adr/ADR-0009`. States that used to need a click are now their own
> stories too, so they are snapshotted rather than merely reachable.
