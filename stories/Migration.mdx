# Migrating custom CSS

OutSystems UI's styling was rebuilt on the **`outsystems-design-tokens`** package.
If your app ships custom CSS that overrode OutSystems UI variables or targeted its
classes, most of it still works — but a specific, enumerable set of things moved.

This page is the complete inventory: **what was retired and what replaces it**,
**what kept its name but changed its value**, and **the new variables that let you
stop writing overrides you previously had to hand-roll**.

> **Partly generated — do not hand-edit the counts, colour tables or the
> compatibility snippet.** They are computed by diffing the pre-migration CSS
> snapshot (`deprecated/`) against the current bundle and resolving the result
> through the design tokens. Regenerate with `npm run docs:migration` (source:
> `scripts/generate-migration-reference.mjs`); everything outside the
> `<generated:…>` markers is hand-written prose.

## The shape of the change

The old library published one flat layer: a `:root` block of ~200 variables
(`--color-red-dark`, `--space-base`, `--shadow-m`, `--font-size-h3`) that components
read directly. Re-skinning meant overriding those, and anything they didn't cover
meant writing a rule against a component class.

Today there are four layers, and each is an override point (see **CSS Architecture**):

```
--osui-{component}-{prop}     per-component / per-instance   ← 460 knobs
        ↓ defaults to
--color-*, --border-radius-*  framework theme roles at :root ← app-wide re-skin
        ↓ defaults to
$token-* / --token-*          design tokens                  ← whole-system re-skin
        ↓ defaults to
primitive literal
```

The practical consequence: **the flat palette variables are gone, the role
variables stayed, and a large new component layer appeared.**

## Shortcut — the compatibility snippet

If you have a lot of custom CSS and want it working again before you have time to
rewrite it, paste this into your app's stylesheet. It re-declares **all 136
retired variables** and points each one at its design-token replacement, so
`var(--space-base)`, `var(--color-indigo-light)` and friends resolve again.

<Callout type="warn" title="It's a bridge, not a destination">
	The snippet restores the <em>names</em>, not the old <em>values</em> — each one now resolves through the token
	chain, so colours follow the new palette. That's deliberate: your CSS stays theme-aware and keeps working if the app
	is re-skinned. It also only serves <em>your</em> stylesheet — OutSystems UI's own components read tokens directly,
	so overriding one of these names will not restyle the library.
</Callout>

## Utility classes: same names, new plumbing

Good news first: **every utility class kept its name**. `.shadow-m`,
`.margin-base`, `.padding-l`, `.border-radius-soft`, `.font-size-h1`,
`.background-primary`, `.text-neutral-0`, `.background-red-lightest` — all still
ship and still work in Service Studio.

What changed is what they read. They now inline the token directly instead of
going through the old variable:

```css
/* before */
.shadow-m {
	box-shadow: var(--shadow-m);
}

/* now */
.shadow-m {
	box-shadow: var(--token-elevation-2, …);
}
```

<Callout type="stop" title="Overriding the old variable no longer re-skins the class">
	Setting <Mono>--shadow-m</Mono> at <Mono>:root</Mono> used to change every <Mono>.shadow-m</Mono> element. It does
	nothing now — override <Mono>--token-elevation-2</Mono> instead. Same for <Mono>{'--space-*'}</Mono> →{' '}
	<Mono>{'--token-scale-*'}</Mono> and <Mono>{'--font-size-*'}</Mono> → <Mono>{'--token-font-size-*'}</Mono>.
</Callout>

Two behaviour notes: `.border-radius-circle` is now a literal `50%` (not a
variable), and `.font-size-h1` applies the full typography role — weight, line
height and letter spacing, not just `font-size`.

## Recipes — "I used to do X"

### "I re-branded the app by overriding `--color-primary`"

Still works, and it's still the right knob for a single brand colour. But
primary now has a **hover** and **pressed** tier, and borders/focus rings derive
from their own tokens — overriding only `--color-primary` leaves those on the
default blue.

```css
:root {
	/* Option A — theme roles: brand colour + its interaction tiers */
	--color-primary: #7c20f2;
	--color-primary-hover: #651ac5;
	--color-primary-active: #5817ab;
	--color-border-primary: #7c20f2;
}
```

```css
:root {
	/* Option B — one level down: every primary-derived token follows,
     including focus halos, subtle backgrounds and component defaults */
	--token-semantics-primary-base: #7c20f2;
	--token-semantics-primary-800: #651ac5;
	--token-semantics-primary-900: #5817ab;
}
```

Prefer **B** for a real re-brand — the focus halo is `color-mix()`-derived from
`--token-semantics-primary-base`, so it recolours automatically.

### "I rounded (or squared) every corner by hand"

There is now one switch for the whole library:

```css
:root {
	--border-radius-default: 0;
} /* everything square */
:root {
	--border-radius-default: 12px;
} /* everything softer */
```

Every radius role (`none`, `soft`, `softer`, `rounded`) falls back to it, so a
single line re-radiuses buttons, inputs, cards, popups and pattern chrome.

### "I restyled one component with `!important`"

That's the case the component CSS API exists for. Each component declares its own
`--osui-{component}-{prop}` variables at its root — 460 of them across the
library (full list on the **CSS API Reference** page). Override the variable
instead of fighting specificity:

```css
/* before */
.my-page .osui-sidebar {
	background: #1a1a2e !important;
}

/* now */
.my-page .osui-sidebar {
	--osui-sidebar-background: #1a1a2e;
	--osui-sidebar-color: #ffffff;
}
```

Because they're custom properties, they cascade: set them on an ancestor to scope
a whole screen, or inline on one element to change a single instance.

### "I set my own body / header / menu backgrounds"

The surface roles are the supported way, and they cover more surfaces than
before:

```css
:root {
	--color-background-body: #f6f7fb;
	--color-background-surface: #ffffff; /* cards, popups, menus, panels */
	--color-background-header: #101828;
	--color-background-sidemenu: #101828;
	--color-background-footer: #101828;
	--color-background-login: #ffffff;
	--color-background-input: #ffffff;
}
```

### "I hand-built a dark mode"

Ship the built-in one instead — add `theme-dark` to the screen's root element:

```html
<div class="theme-dark">…</div>
```

It's implemented purely as variable overrides, so it composes with your own
`--osui-*` and `--color-*` customisations. It is **opt-in and manual** — there is
no `prefers-color-scheme` auto-switch; toggle the class yourself if you want to
follow the OS.

### "I changed all the shadows / all the spacing / all the type"

Override the tokens, not the components:

```css
:root {
	--token-elevation-2: 0 2px 8px rgba(0, 0, 0, 0.12);
	--token-scale-400: 20px; /* every 16px gap becomes 20px */
	--token-font-size-400: 15px;
}
```

### "I styled form validation states"

These are roles now, split by the property they colour:

```css
:root {
	--color-error: #d82424; /* fills / accents */
	--color-text-danger: #b91c1c; /* the validation message */
	--color-border-danger: #d82424; /* the field outline */
}
```

### "I customised focus outlines for accessibility"

Focus is a single primary-derived halo, exposed as
`--osui-border-focus-halo` (and read by `--color-focus-outer`). The old
yellow/inner pair is gone:

```css
:root {
	--osui-border-focus-halo: color-mix(in srgb, #7c20f2 30%, transparent);
}
```

Remember the `has-accessible-features` body class still gates the enhanced focus
affordances — you can toggle it in this Storybook's **A11y features** toolbar.

2. **Grep before you look.** The retired names are a finite list; searching your
   stylesheets for `--space-`, `--font-size-`, `--shadow-`, `--border-size-` and
   `--color-` followed by a family name will find most of the work mechanically.
3. **Expect silent failures, not build errors.** A declaration that reads a retired
   variable is simply dropped. Those are the ones that show up as "the page looks
   slightly off" rather than as something obviously broken.
4. **Delete, don't port, the `!important` overrides.** Most of them existed because
   there was no variable. Check the **CSS API Reference** for the component first —
   there usually is one now.
