# CSS Architecture

How OutSystems UI styles every component: three cooperating layers — **design
tokens**, a **framework theme layer at `:root`**, and a per-component **CSS API** —
tied together by a single resolution chain, and all shipped inside a **CSS cascade
layer** so apps can override it without specificity fights. This is the Storybook
summary; the full write-up lives in `docs/css-architecture.md`, and every
`--osui-*` property is catalogued on the **CSS API Reference** page.

## The big picture

Every property resolves through a **four-hop chain**. Each hop is one layer with
one job, and each has a sensible default so the layer below is optional:

<HopChain />

Traced through the Card background, top to bottom:

```scss
.card {
  --osui-card-background: var(--color-background-surface); // Component API → theme role
}
background-color: var(--osui-card-background);             // property → Component API
```

```scss
// Framework theme layer — src/scss/01-foundations/_root.scss
:root { --color-background-surface: #{$token-bg-surface-default}; } // role → token
```

```scss
// Design tokens — src/scss/tokens/_variables.scss  (generated)
$token-bg-surface-default: var(--token-bg-surface-default, var(--token-primitives-base-white, #ffffff));
```

**Anyone can intercept at any hop:** an app sets `--token-bg-surface-default` to
re-skin globally, a theme sets `--color-background-surface` to change just the
surface role, and a single instance sets `--osui-card-background` to override one
card — none of them touch a component rule.

---

## Tier 1 — Design tokens (`--token-*` / `$token-*`)

The bottom layer comes from the `outsystems-design-tokens` package and is
**generated**, never hand-edited:

```bash
npx build.tokens --dest src/scss/tokens/ --prefix token   # runs in prebuild / predev
```

It emits two cooperating surfaces (both gitignored):

| Surface | What | Use it when |
|---|---|---|
| `$token-*` SCSS vars | each expands to `var(--token-*, <fallback>)` | **writing component SCSS** — gives compile-time checking + a baked-in fallback |
| `--token-*` at `:root` | raw values | the **runtime theming surface** an app/DTE overrides |

Tokens are themselves layered — **primitives → semantics → component** — and the
fallback chain encodes it: a semantic token (`bg-surface-default`) falls back
through a primitive (`primitives-base-white`) which falls back to a literal, so a
component renders correctly even if no `--token-*` are defined at runtime.

> **Verified:** the compiled bundle does **not** ship the `--token-*` `:root`
> block — it relies on the `var(--token-*, fallback)` fallbacks. The generated
> `tokens/_root.scss` is the canonical override set an app supplies at `:root`.

Rules of thumb:

- CSS **property value** → write `$token-*` directly: `padding: $token-scale-600;`
- CSS **custom-property declaration** → interpolate: `--osui-card-padding: #{$token-scale-600};`
- Retired, never reintroduce: `--space-*`, `--font-size-*`, `--shadow-*`, `--border-size-*`, and the `get-*-color()` helpers.

---

## Tier 3 — Framework theme layer at `:root`

`src/scss/01-foundations/_root.scss` declares OUI's stable, framework-owned
theming contract — un-prefixed role knobs that sit between tokens and components.
Each defaults **through** a `$token-*`, so overriding the token still cascades.

```scss
:root {
  --color-background-surface: #{$token-bg-surface-default};
  --color-text:               #{$token-text-default};
  --color-primary:            #{$token-semantics-primary-base};

  // one shape vocabulary; set --border-radius-default once to re-radius everything
  --border-radius-soft:   var(--border-radius-default, #{$token-border-radius-200}); // 8px
  --border-radius-softer: var(--border-radius-default, #{$token-border-radius-400}); // 16px
  --border-radius-rounded:var(--border-radius-default, #{$token-border-radius-full});// 999px
}
```

| Group | Vars |
|---|---|
| Surfaces | `--color-background-{body,surface,header,sidemenu,footer,login,input,…}` |
| Text | `--color-text`, `--color-text-{subtle,subtlest,disabled,inverse}` |
| Borders | `--color-border`, `--color-border-{subtle,subtlest,input,…}` |
| Brand / status / neutral | `--color-{primary,secondary,error,warning,success,info}`, `--color-neutral-0..10` |
| Radius | `--border-radius-{none,soft,softer,rounded}` |

App-layout plumbing also lives in `_root.scss` but is **not** part of the theme
contract: `--size-*`, z-index `--layer-*`, and safe areas `--os-safe-area-*`.

---

## Tier 4 — Component CSS API (`--osui-*`)

Every visual component declares its own custom properties at its root selector,
defaulting either to a theme role (themeable props) or straight to a `$token-*`
(structural props), then reads them in property values:

```scss
.card {
  --osui-card-background:    var(--color-background-surface);   // → theme role (themeable)
  --osui-card-border-width:  #{$token-border-size-025};         // → token directly (structural)
  --osui-card-border-radius: var(--border-radius-soft);
  --osui-card-padding:       #{$token-scale-600};
  --osui-card-shadow:        #{$token-elevation-1};

  background-color: var(--osui-card-background);
  border-radius:    var(--osui-card-border-radius);
  padding:          var(--osui-card-padding);
}
```

Rules:

- Naming: `--osui-{component}-{property}`.
- Property declarations **must** go through the `--osui-*` var (never directly
  through `$token-*` / `--color-*`), so a consumer can override one instance
  without touching tokens or the theme.
- Route **themeable** props through the theme role, **structural** props straight
  to `$token-*`.

See the **CSS API Reference** page for the full list of every `--osui-*` property
and its default.

## Theming & dark mode

A theme is **entirely CSS-custom-property overrides** scoped under a single class
(or a media query). It overrides theme-layer roles and/or the underlying tokens —
never a component rule.

```css
:root          { --color-primary: #6d28d9; }            /* re-skin one role */
:root          { --token-bg-surface-default: #1b1b1b; } /* re-skin globally via a token */
:root          { --border-radius-default: 12px; }       /* round every corner */
.card.is-promo { --osui-card-shadow: var(--osui-elevation-overlay); } /* one instance */
```

> **Invariant:** if a theme needs to touch a *component rule*, that's a leak in
> the component's CSS API — fix it in the component, not the theme.

**Dark theme** (`src/scss/01-foundations/_theme-dark.scss`) ships and is opt-in,
**manual only**:

- Add `.theme-dark` to `<body>` (the screen's outermost element) to switch to
  dark; remove it for the default light palette.
- There is **no OS auto-detection** — an app that wants to follow the OS reads
  `prefers-color-scheme` itself and toggles the class.

It re-maps the dark `--token-*` **and** re-declares the `--color-*` roles (needed
because `--color-*` is substituted at `:root`, so a token override on `<body>`
alone wouldn't reach components reading `--color-*`).

> Try it: use the **Appearance** toolbar control above to switch Light / Dark
> across any story.

## Overriding the library — cascade layers

The three tiers above are for overriding **values**. But when you need to override
a **rule** with no `--osui-*` knob — a layout, a pseudo-element, a deep state
selector — the whole compiled bundle ships inside a CSS **cascade layer**, with
ordered sublayers:

```css
@layer outsystems-ui {
  @layer vendor, root, reset, base, patterns, utilities;
  /* every OutSystems UI rule, routed into one of the sublayers above */
}
```

Because **unlayered styles always beat layered styles regardless of specificity**,
any ordinary CSS your app writes wins — no specificity match, no `!important`:

```css
/* App CSS (unlayered) — beats the layered framework rule despite lower specificity */
.osui-dropdown-serverside__selected-values-wrapper { border-color: blue; }
```

<LayerStack />

The sublayers make the framework's own precedence explicit: **`utilities` always
beats `patterns`** (a single utility class wins over a deeply nested pattern rule),
and **`vendor` always loses** to OSUI's own provider overrides. You can target one
slice — e.g. reskin only the vendor baselines with `@layer outsystems-ui.vendor { … }` —
but the common case is just writing unlayered app CSS.

**Guidance:**

1. **Prefer the custom-property APIs** (the tiers above) — cleanest and survives
   restructuring. Reach for a raw rule override only when no property is exposed.
2. **Keep your overrides unlayered** and they always win. If your app uses its own
   layers, declare order up front so yours stay on top: `@layer outsystems-ui, app;`
3. **Two things a layer cannot beat:** platform-injected **inline styles** (still
   need `!important`) and the framework's own `!important` declarations (importance
   outranks layer origin, so match it with `!important`).

> **Verified:** the bundle is entirely inside the layer (no stray unlayered rules),
> and layering does not change the framework's own rendering — within a sublayer,
> specificity + source order behave as before; only cross-sublayer precedence is
> made explicit. See `specs/cascade-layers.md`.

## Authoring quick-reference

Walk **down** the chain only as far as you need:

1. Reading a **themeable** colour/radius? → use the theme role: `var(--color-*)`, `var(--border-radius-*)`.
2. Reading a **structural** size/space/elevation/border? → use `$token-*` directly.
3. Exposing it on a component? → declare `--osui-{component}-{prop}` defaulting to (1) or (2), and read the `--osui-*` var in the property.

**Red flags:** hardcoded hex/px where a `$token-*` exists; reintroducing retired
vars; a property reading `$token-*` / `--color-*` directly instead of via its
`--osui-*`; a theme touching a component rule.
